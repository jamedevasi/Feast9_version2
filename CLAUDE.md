# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Repository state

The app is under active, phased construction, built directly against `feast9_v2_agents.md`. It is now a git repository (`origin` = https://github.com/jamedevasi/Feast9_version2.git). Built so far:

- **Phase 1 — Foundation + Patients**: app factory, auth (setup/login/logout, PBKDF2, CSRF, DB-backed rate limiting, security headers), patient registration/search/detail.
- **Phase 2 — Cases**: full 9-section case detail (Consent Forms, Visit Notes, Prescriptions, Clinical Attachments, Lab Requisitions, Referral Notes, Payment Log, Follow-up & Next Action, Cost History & Revisions), wired into the patient detail page.
- **Phase 3 — Appointments**: `appointment_routes.py` (calendar month view, new/edit/delete), doctor-colour-coded month grid, patient-detail Appointments section, "📅 Book Appointment" link on a case's Follow-up section (`clear_followup` flow — clears the case's follow-up once the appointment is booked), no-show → next-day follow-up logic in `_save_appointment`'s edit path (not a separate status route), click-to-copy WhatsApp/SMS reminder text on the edit page.
- **Recurring appointments (§14 item — UI/UX was explicitly left open by §15)**: a bounded set of *real* appointment rows is generated up front (capped at `MAX_RECURRING_OCCURRENCES` = 52), not a virtual/computed series — so exceptions (edit or delete one generated row), per-occurrence no-show handling, and conflict detection all reuse the existing single-appointment machinery instead of needing a separate recurrence engine. Additive `appointments.series_id` column (self-referential FK, `_migrate_appointments_recurring`) ties every occurrence, including the first, to the same value. `db.add_recurring_appointments` steps by `RECURRENCE_INTERVALS` (`Weekly`/`Biweekly`/`Monthly`, via `db._nth_occurrence`/`_add_months` — see the "Follow-up lifecycle" entry below for why occurrences are counted from the start date and Sundays move rather than skip), and flags (doesn't block) same-doctor/overlapping-time conflicts against existing appointments (`db._find_conflicts`) as a flashed warning per occurrence. Editing an occurrence offers exactly two scopes per §14's literal "edit-one-vs-edit-series" framing: **this occurrence only** (normal single-row update, e.g. status/no-show/date) or **the whole series** (`db.update_appointment_series` — doctor/time/title/notes only, deliberately excludes date and status, and only touches rows still `Scheduled` so a `Completed`/`Cancelled`/`No-show` occurrence's history is never rewritten). `db.cancel_appointment_series` is the bulk-cancel action, same "only touch `Scheduled` rows" rule. Calendar shows a 🔁 badge on any appointment with a `series_id`. See `tests/test_appointments.py`'s recurring-appointment tests, including one asserting a `Completed` occurrence is untouched by a series-wide edit/cancel.
- **Dental charting (§14 item — "biggest clinical gap," structured data is the source of truth, SVG is presentation-only)**: new `dental_chart_entries` table, **append-only** like visit notes/prescriptions — a correction is a new entry, never an edit of an old one; the append-only log itself is the "correction/version history" the spec asks for. FDI/ISO 3950 tooth notation (`app/constants.py`: `PERMANENT_TEETH_UPPER/LOWER` = 11-48, `PRIMARY_TEETH_UPPER/LOWER` = 51-85 — both dentitions are always chartable together, no per-patient dentition setting, since mixed dentition is real). Each entry records tooth, surface (`TOOTH_SURFACES`), finding (`CHART_FINDINGS`: Sound/Caries/Restoration/Crown/Root Canal/Implant/Missing-Extracted/Fracture/Other), status (`CHART_STATUSES`: Existing/Planned/Completed — covers "planned-vs-completed treatment"), an optional `case_id` association, notes, and `recorded_by`/`recorded_at`. `db.add_dental_chart_entry` forces `surface = "Whole Tooth"` for `WHOLE_TOOTH_FINDINGS` (Missing/Extracted, Crown, Root Canal, Implant) regardless of what was submitted — a crown can't be "on the mesial surface." `db.get_current_dental_chart` derives the *current* state per tooth from the log: latest entry per (tooth, surface), except a tooth whose overall-latest entry is Missing/Extracted shows only that (a pulled tooth has no surfaces left to show findings on). The chart itself (`dental_chart.html`) is a hand-written inline `<svg>` — a small coloured rect + FDI number per tooth, clickable (plain `<a href="?tooth=..">`, no JS, CSP-safe) to jump to the entry form pre-filled for that tooth — genuinely a presentation layer over the query above, not a separate data source. No role restriction beyond `login_required`, matching the existing visit-notes/prescriptions pattern (only financial data is receptionist-restricted). Entry creation is audited (`dental_chart_entry_added`) with structured fields only (tooth/surface/finding/status) — notes content is never logged, matching the redaction pattern for other free-text clinical fields. Linked from patient detail via a "🦷 Dental Chart" button (its own page, not embedded — patient/case detail's fixed section orders are untouched). See `tests/test_dental_chart.py`, including the Missing/Extracted-supersedes-older-findings test and the append-only-history-is-never-shortened test.
- **Phase 4a — Multi-user roles (§14 item)**: `admin` table extended (additive `role`/`is_active` columns via `_migrate_admin_roles`) to hold every account, not just the bootstrap admin. Three roles: `admin`, `doctor`, `receptionist`. `app/routes/user_routes.py` (admin-only `/users` list/create/deactivate/reactivate, blocked from deactivating the last active admin). `app.auth.role_required(*roles)` and `financial_access_required` (blocks `receptionist`) enforce access server-side — applied to `add_payment`/`revise_cost` in `case_routes.py`. Case detail's `detail()` route redacts `total_cost`/`payments`/`balance`/`cost_revisions` entirely out of the render context for receptionist sessions (never sent to the client, not just CSS-hidden); `case_sections/payments.html` and `cost_history.html` show a "Restricted" notice in that case, preserving the fixed section order. Case creation silently zeroes any `total_cost` a receptionist session posts, regardless of what's in the form. See `tests/test_roles.py` for the enforcement tests (403s on every financial route/record for receptionist, admin/doctor unaffected).
- **Phase 4b — Audit log (§14 item)**: additive `audit_log` table (`actor_user_id, role, ts_utc, action, entity, entity_id, correlation_id, before_summary, after_summary, ip, user_agent, outcome`). `db._write_audit(conn, ...)` takes the caller's already-open connection and does **not** commit/close — every instrumented db.py write function (`update_patient`, `close_case`, `record_case_consent`, `add_visit_note`, `add_prescription`, `add_payment`, `update_case_cost`, `add_attachment`, `create_user`, `set_user_active`) inserts its audit row in the same transaction as the action it records. `db.write_audit_now()` is the one exception — a standalone commit for attachment *downloads* (`clinical.serve_attachment`), which has no other write to piggyback on. Summaries are field-level/redacted by construction: patient edits log changed field *names* only (never values — allergies/medical conditions are sensitive), visit notes/prescriptions log a length + date (never the clinical text), consent logs the fact only. Financial actions (payments, cost revisions) do log amounts — that's the point of a financial audit trail, not a redaction gap. Admin-only viewer at `/audit-log` (`app/routes/audit_routes.py`). See `tests/test_audit_log.py`, including the check that sensitive field values never appear in a logged row.
- **Phase 4c — TOTP 2FA (§14 item)**: `pyotp` (codes) + `qrcode` (SVG QR, no Pillow dependency — `qrcode.image.svg.SvgPathImage`). Additive `admin` columns `totp_secret`, `totp_enabled`, `totp_recovery_codes_json`. Self-service enrollment at `/totp/setup` (`app/routes/totp_routes.py`) — scan QR or enter the key manually, confirm with a live code, then one-time recovery codes are shown exactly once (`/totp/recovery-codes`, session-only, hashed at rest same as passwords). Login becomes two-step when `totp_enabled`: password success stores `totp_pending_user_id`/`totp_pending_next` in session and redirects to `/login/totp` (code or a recovery code — recovery codes are consumed on use, `db.consume_recovery_code`) rather than completing the session; `admin_id` is only set after the second factor passes. **Step-up re-authentication** (§14: "not just an active session") is `app.auth.reauth_required` — a session's `reauth_at` is stamped fresh at every successful login (password-only or TOTP-completed) and must be within `REAUTH_WINDOW_MINUTES` (10) or the decorator redirects to `/reauth` (password, +code if enabled) before continuing; applied to `/users/new`, `/users/<id>/deactivate`, `/users/<id>/activate`, `/users/<id>/reset-totp`, and `/totp/disable` — the "user management" and "TOTP reset" items from §14's high-risk-action list (backup/restore and bulk import/export aren't built yet, so not wired up). Admin can force-reset another user's TOTP from `/users` (audited as `totp_reset`). See `tests/test_totp.py`, including a test that manipulates `session_transaction()` to prove a stale (10+ minute) session is rejected until it steps up.

- **Threat model (§14 item)**: `THREAT_MODEL.md` covers the six areas §14 names by name (receptionist misuse of scheduling-only access, export/PDF paths, shared front-desk devices, stolen sessions, backup file exposure, uploaded clinical files) — assets, actors, current mitigations with file references, and residual risks. It originally flagged two real gaps — no idle/absolute session timeout, and no session revocation on deactivation/TOTP-reset — both since fixed (see the session logout entry below). Revisit it when PDF generation, Excel import, Google sign-in, or the patient portal are built — each is called out in the doc as a likely trigger.
- **Automated off-server backup (§14 item)**: `app/backup.py` — `create_backup()`/`restore_backup()`. A consistent DB snapshot via SQLite's own backup API (safe under WAL) + `clinical_uploads/` are tarred and encrypted with Fernet (`cryptography`, key in `BACKUP_ENCRYPTION_KEY`, deliberately independent of `SECRET_KEY`); refuses to run at all if the key isn't set rather than ever writing an unencrypted backup. Off-site push is a pluggable shell command (`BACKUP_OFFSITE_COMMAND`, `{file}` placeholder) — provider choice (S3/B2/second server, via rclone/rsync) stays a deferred operational decision per §15, not hardcoded. `run_backup.py` (schedule nightly via cron/Task Scheduler) and `restore_backup.py` (CLI-only, never a web route — makes a safety copy of the current DB, refuses to overwrite without `--force`) at the repo root; full setup/scheduling/restore-testing instructions in `BACKUP.md`. Admin-only `/backup` (`app/routes/backup_routes.py`) lists history and lets an admin run one on demand or download a past one — both `reauth_required`, both audited (`backup_created`, `backup_downloaded`). Dashboard shows a warning banner to admins if the last backup failed, never ran, or is more than 26h stale. See `tests/test_backup.py`.
- **Clinical document retention/deletion (new requirement, added by the user 2026-09-16 — not in `feast9_v2_agents.md`'s original §5.4)**: retention needs vary per case — some cases must keep lab reports/X-rays/photos after closing, others don't — so purging clinical attachments is a deliberate, per-case choice for the practitioner (doctor/admin) to make, never automatic and never available to the receptionist role. `clinical.delete_attachment` (single file) is now `role_required("admin", "doctor")` + `reauth_required` and writes an `attachment_deleted` audit row (file type + optional reason, never file content). A new bulk action, `clinical.clear_attachments` (`db.clear_case_clinical_documents`), deletes every attachment for a case in one go — same role/reauth gating, plus a **required** reason (unlike the single-file delete, where a reason is optional) — and writes one `clinical_documents_cleared` audit row summarizing the count and file types removed. Both are hidden from the receptionist role in `case_sections/attachments.html`, not just blocked server-side. See `tests/test_attachments.py` for the role/reauth/reason enforcement tests.
- **DPDP Phase 2 — data-rights requests (§5.11 item)**: new `data_requests` table (exact spec DDL) plus additive `patients.is_anonymized`/`anonymized_at` columns. Four request types (Access, Correction, Erasure, Withdraw Consent); `db.create_data_request` sets a 90-day `deadline_at` automatically. Any logged-in role can log a request (`/patients/<id>/data-requests/new` — front desk commonly takes these first), but resolving one (`dpdp.resolve`, `db.resolve_data_request`) is `role_required("admin", "doctor")` + `reauth_required`. `resolve_data_request` applies the request's real effect in the **same transaction** as the status change: completing an **Erasure** soft-anonymises the patient row (name → `Erased Patient #<id>`, DOB/mobile/email/address/emergency+guardian contacts cleared, `comms_consent` cleared) but never touches cases/visit notes/prescriptions/payments/cost_revisions — and requires `confirm_name` to exactly match the patient's current name first, raising `ValueError` (no writes at all) on a mismatch, per spec's "type the patient's exact name to confirm" safeguard; completing **Withdraw Consent** clears `comms_consent`/`comms_consent_at`; Access/Correction have no automated side effect beyond the status change (the actual correction happens through the normal patient-edit form, already audited separately). `count_pending_data_requests()` is injected into every logged-in page via a Flask context processor (`app/__init__.py:_register_context_processors`) and shown as a nav badge. Patient detail's existing, order-fixed "Contact Details & DPDP Status" section (§5.2 — order itself untouched) gained a nested request list + an anonymized-patient banner, rather than a new top-level section. See `tests/test_dpdp.py`, including the erasure test that asserts case/payment/balance data is untouched after anonymisation.

- **PDF generation (§10)**: `app/pdf_reports.py` — all 7 generators from the spec's table, each returning `bytes` via `SimpleDocTemplate`/`BytesIO` (never writes to disk), sharing a `_header()`/`_table()`/`P()` toolkit built on ReportLab's base-14 Helvetica. Every piece of free-form, user-typed text (rx details, referral reason/notes, consent notes, case/patient names, payment method/reference, ...) is XML-escaped before it reaches a `Paragraph` or a `Table` cell — ReportLab's `Paragraph` parses its content as mini-XML, so an unescaped `&`/`<`/`>` in a note would otherwise raise or corrupt the layout; verified directly with adversarial `&`/`<`/`>`-laden mock data against all 7 generators. `generate_prescription_pdf` shows an "ALLERGY ALERT" banner when the patient has any recorded allergy. `generate_consent_pdf` always renders "Paper consent on file" rather than an embedded signature image — signature capture itself is still out of scope (see the "Tables not in original spec" note below). `generate_report_pdf` takes the exact same context dict `reports_routes._report_context()` builds for the on-screen page, so the PDF and the HTML report can never drift apart. Routes: `/cases/<id>/prescriptions/<rx_id>.pdf`, `/cases/<id>/summary.pdf`, `/cases/<id>/consent.pdf` (case-level, all `login_required` only — case-summary redacts financial figures per `can_view_financial_data()` rather than blocking the route outright, since it's primarily a clinical document); `/patients/<id>/summary.pdf` (same redaction approach); `/cases/<id>/referral/<ref_id>/print` (the literal path §5.6/§10 specify); `/reports/report.pdf` (`financial_access_required`, replaces the `reports_print.html`/`/reports/print` browser-print stand-in from the Reports phase — both were deleted now that real PDF generation exists); `/data-requests/<id>/access.pdf` (DPDP Phase 2 right-to-access export, `role_required("admin","doctor")` — unlike the audit log's redaction-by-design, this PDF includes full clinical text, since the entire point is handing the patient their own data). All 7 generators are smoke-tested for `%PDF` magic bytes per the spec's own test-checklist item 26. **`generate_data_access_pdf` initially omitted visit notes and dental chart history** despite its own docstring claiming full clinical text — fixed 2026-09-17 (patient-portal design discussion surfaced it: with the portal excluded for now, this PDF is the actual mechanism for fulfilling an Access request, so it has to be complete). Added `db.list_visit_notes_for_patient` (mirrors the existing `list_prescriptions_for_patient` cross-case pattern) and reused the existing `db.list_dental_chart_entries` (the full append-only log — not `get_current_dental_chart`'s derived-latest-state view, since a right-to-access export covers everything on file, not just the current summary). See `tests/test_pdf_generation.py` and the `report.pdf`/redaction tests folded into `tests/test_reports.py`.

## Non-negotiable requirements (do not "fix" or soften these)

These are stated as settled in `feast9_v2_agents.md` and must not be treated as open questions, regardless of what the secondary planning docs suggest:

- Sex field is `Male` / `Female` only — no other options.
- A receptionist role (once built) must have **zero** access to financial data (payments, costs, balances, revenue reports/exports/PDFs, backups), enforced server-side on every route — never UI-only.
- DPDP Act 2023 compliance (data notice, consent, data-rights requests) must never be diluted; the documented DPDP rules do not require external legal review before implementation.
- Follow-up (a dashboard reminder on a case) and Appointment (a confirmed calendar booking) are distinct concepts and must never be conflated in UI or logic.
- Additive-only DB migrations — never drop or rename columns (`arrived_at`/`seen_at` are deliberately retained, unused columns from a removed feature).
- Clinical document deletion/retention is a **practitioner-only** decision (added by the user 2026-09-16, not in the original `feast9_v2_agents.md`) — the receptionist role must never be able to delete a clinical attachment, single or bulk, enforced server-side; retention varies by case (some cases must keep lab reports/X-rays after closing, others don't), so there is no automatic purge-on-close — deletion is always an explicit doctor/admin action with a reason recorded.

## Architecture (as built)

A **no-build-step Flask + raw-SQLite** system — no ORM, no frontend framework:

- `app/db.py` is the only file that touches SQLite directly; all other modules go through it. It uses an explicit column-whitelist pattern for every insert/update (see `add_patient`/`update_patient`, `add_case`/`update_case`) — never build SQL column lists from raw request-derived dict keys.
- Routes are split into per-domain blueprints under `app/routes/`, each registered in `app/__init__.py`: `auth_routes.py`, `patient_routes.py`, `case_routes.py` (case core + visit notes + prescriptions + payments + cost revisions + follow-up + consent), `clinical_routes.py` (attachments + lab requisitions + referral notes — grouped per feast9_v2_agents.md's own file layout), `dashboard_routes.py`.
- The case detail page (`templates/case_detail.html`) composes its 9 fixed-order sections via `{% include %}` of `templates/case_sections/*.html` partials — add new case sub-features as a new partial + route, not by growing case_detail.html directly.
- Clinical file uploads are stored outside the web root (`DATA_DIR/clinical_uploads/`), UUID-named, validated by magic bytes only (`app/validators.py:detect_upload_type` — never trust the client-supplied extension), served only through an authenticated route (`clinical.serve_attachment`).
- CSRF validation (`app/csrf.py`) is required on every POST. Every page with a logged-in nav (`base.html`) renders a second hidden CSRF input in the logout form — when scripting against the app (curl, tests), take the *first* `csrf_token` match on a page, not the count.
- Case detail and patient detail each have a fixed, non-negotiable section order — see §5.2/§5.3/§8 of `feast9_v2_agents.md` before touching those templates. Section-order regressions are caught by `test_patient_detail_section_order` / `test_case_detail_section_order`.
- Visit notes, prescriptions, and payments/cost-revisions are **append-only** (no edit/delete routes) — intentional, matches the "controlled correction process, not silent destructive editing" principle for clinical/financial records.
- `total_cost` on a case only ever changes via `db.update_case_cost()`, which inserts a `cost_revisions` row automatically when the value actually changes. Never `UPDATE cases SET total_cost` directly.
- CSP is `script-src 'self'` with no inline scripts anywhere — any new client-side behavior goes in a static `.js` file (see `patient_form.js`, `referrals.js`), not an inline `<script>` block **or an inline `on*=` attribute** (also blocked, silently). For a confirmation prompt use `data-confirm="..."` on the form (`ui_actions.js`).
- Not yet in scope: reports queries needing `DATE()` wrapping on timestamp columns, and the no-show → follow-up appointment logic — both apply once Appointments/Reports are built (see §5.9/§5.7 of the spec).

## Tables not in the original spec

`feast9_v2_agents.md` §4 never defined DDL for `admin`/`login_attempts` (auth), `case_visit_notes`, `prescriptions`, `payments`, or `cost_revisions`, despite requiring the features that need them. These were designed during the build (see `app/db.py`) following the spec's own conventions (additive, `CREATE TABLE IF NOT EXISTS`, explicit timestamps). The `cases` table also has three columns beyond the spec's literal DDL — `consent_recorded`, `consent_recorded_at`, `consent_notes` — needed for the "red border if no consent" rule; `generate_consent_pdf` (`app/pdf_reports.py`) exists now but always renders "Paper consent on file" rather than an embedded signature — signature capture itself is still out of scope. The `admin` table gained `role`/`is_active` columns (Phase 4, additive `ALTER TABLE` in `_migrate_admin_roles`) — it holds every user account (admin/doctor/receptionist), not just the bootstrap admin; the table name was kept as-is to avoid a pointless rename. The `patients` table gained `is_anonymized`/`anonymized_at` columns (DPDP Phase 2, additive `ALTER TABLE` in `_migrate_patients_dpdp`) for the Erasure request type's soft-anonymisation.
